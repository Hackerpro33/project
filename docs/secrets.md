# Управление секретами

Этот документ описывает единый процесс работы с секретами, внедрённый после перехода на SOPS/age.

## Основные принципы

- **GitOps-подход.** Шифрованные файлы `secrets/<environment>.secrets.yaml` хранятся в репозитории и
  применяются через GitOps/CI-пайплайны. Расшифровка выполняется только в доверенных окружениях.
- **Однозначная структура.** Каждая секция содержит подмножество ключей:
  - `env` — переменные окружения, которые необходимо экспортировать перед запуском сервисов.
  - `rotation` — политика обновления секретов (каденс, ответственные, процедура экстренной смены).
  - `metadata` — служебная информация (дата последней ротации, ссылка на инцидент, если применимо).
- **Минимизация поверхностей.** Доступ к ключам выдаётся через age-идентификаторы; список получателей
  ведётся в инфраструктурном репозитории и сверяется при code review.

## Подготовка окружения

1. Сгенерируйте age-ключи для членов команды безопасности и CI (см. [официальную документацию](https://age-encryption.org/)).
2. Сформируйте файл на основе `secrets/example.secrets.yaml`, заполните поля в секциях `env` и
   `rotation`.
3. Зашифруйте файл:

   ```bash
   sops -e --age age1example... secrets/example.secrets.yaml > secrets/prod.secrets.yaml
   ```

4. Добавьте файл в git и настройте GitOps-оператор (ArgoCD/Flux), который будет расшифровывать и
   прокидывать переменные в окружение.

## Ротация секретов

- **Плановая ротация:** не реже одного раза в квартал. Ответственный инженер инициирует issue,
  обновляет значения, пересобирает секрет, фиксирует дату в секции `rotation.history`.
- **Экстренная ротация:** при утечке или подозрении на компрометацию секрет меняется немедленно.
  Новые ключи разворачиваются через GitOps, после чего команды получают уведомление в Slack/Email.
- **Аудит:** результаты ротаций и расшифровок логируются в централизованном хранилище. Рекомендуется
  подключить оповещения при превышении частоты расшифровок или несоответствии получателей.

## Интеграция с CI

- Workflow `ci.yml` может использовать переменную `INSIGHT_SECRETS_FILE`, указывающую на путь к
  расшифрованному файлу. При локальной разработке можно выполнить `sops -d ... > runtime.secrets.yaml`
  и передать путь через переменную окружения.
- Workflow `sca.yml` работает аналогично и не хранит секреты в открытом виде, опираясь на токены,
  предоставленные провайдером Runner'а.

Соблюдение данных процедур позволяет отказаться от `.env` файлов и обеспечить прозрачную историю
изменений секретов.
