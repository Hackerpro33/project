# ADR-0001: Переход с файлового хранилища на Postgres

- Статус: Accepted
- Дата: 2024-05-18 (обновлено 2025-02-19)

## Контекст

Текущее файловое хранилище ограничивает возможности совместного доступа, транзакционности и
масштабирования. Поддержка аналитики, фоновых задач и пользовательских дашбордов усложняется без
централизованной БД. Переход к Postgres позволяет хранить метаданные загрузок и результаты
обработки в одном источнике правды, а также упростить аудит.

### Драйверы решения

- Требования к строгой консистентности между API, воркерами и UI.
- Поддержка транзакций и миграций, необходимых для новых функций (дашборды, совместный доступ).
- Необходимость SQL-интерфейса для аналитических запросов и SLA по времени ответа.
- Поддержка RPO ≤ 15 минут и RTO ≤ 30 минут при инцидентах хранения.

## Решение

- Использовать Postgres как основную СУБД для метаданных загрузок, профилей данных и задач.
- Определить модели данных на SQLModel/SQLAlchemy и поддерживать миграции через Alembic.
- Настроить docker-compose сервис `postgres` и переменные окружения в SOPS-манифесте (`secrets/<env>.secrets.yaml`).
- Обновить слой доступа к данным, чтобы избавиться от зависимостей от локальной файловой системы.
- Ввести регулярные резервные копии (`pg_dump`) и хранить их в объектном хранилище с TTL ≥ 30 дней.

## Рассмотренные альтернативы

| Альтернатива | Причина отказа |
| --- | --- |
| Продолжать использовать файловую систему + JSON метаданные | Нет транзакций, сложно масштабировать, высокий риск несогласованности. |
| SQLite | Не подходит для горизонтального масштабирования и параллельных записей. |
| Использовать специализированное хранилище данных (BigQuery/ClickHouse) | Избыточно для OLTP сценариев, сложнее организовать миграции и локальную разработку. |

## Последствия

Положительные:

- Транзакционность и согласованность данных.
- Улучшенная схема для аналитики и агрегированных запросов.
- Готовность к горизонтальному масштабированию API и воркеров.
- Поддержка отказоустойчивых бэкапов и контрольных точек для SLA.

Негативные:

- Необходимость администрирования Postgres.
- Увеличение сложности деплоя и миграций.
- Требуются дополнительные ресурсы на CI для поднятия базы данных.

## Риски и меры смягчения

- **Рост задержки запросов** — включаем индексы и делаем периодический анализ `EXPLAIN` для ключевых запросов.
- **Конфликты миграций** — включаем ревью схемы через CODEOWNERS и обязательный прогон Alembic.
- **Проблемы с резервным копированием** — настраиваем ежедневный `pg_dump` и еженедельные проверки восстановления.

## План внедрения

1. Описать модели данных и миграции.
2. Создать слой репозиториев для CRUD-операций.
3. Настроить фикстуры баз данных в тестах и обновить контрактные тесты API.
4. Обновить документацию и скрипты развёртывания.
5. Настроить мониторинг Postgres (pg_stat_statements, health-check) и регламент аварийного восстановления.
