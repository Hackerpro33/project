# Спецификации развития загрузок и обработки

Документ фиксирует инициативы по расширению возможностей загрузки данных и фоновой обработки. Каждая функция описывает целевую ценность, ключевые сценарии, UX-требования и технические зависимости.

## Множественные загрузки и параллельная обработка — ★★★, команда M

**Цель.** Пользователь может отправить несколько файлов за одну сессию, контролировать статус каждой задачи и оперативно реагировать на ошибки.

**Основные возможности.**

- Очередь загрузки с поддержкой drag-and-drop и выбором нескольких файлов.
- Параллельное размещение задач в очереди обработки с ограничением по количеству одновременных воркеров.
- Индивидуальные индикаторы прогресса (загрузка, валидация, обработка) и общий статус всей пачки.
- Повторная отправка упавших задач без перезагрузки страницы.

**UX/технические требования.**

- API `/api/v1/uploads/batch` принимает multipart-запрос с несколькими файлами и метаданными.
- Поддержка `Idempotency-Key` для батча и индивидуальных `upload_id` для отслеживания прогресса.
- Воркеры RQ обрабатывают задачи параллельно, учитывая лимит `MAX_CONCURRENT_JOBS`.
- Websocket или server-sent events для обновления прогресса без polling-нагрузки.

**Зависимости.** Конфигурируемый пул воркеров, расширенная модель статусов задач, обновление фронтенд-компонентов очереди.

## Версионирование файлов — ★★, команда M

**Цель.** Обеспечить хранение истории загрузок и возможность отката к прошлой версии данных.

**Основные возможности.**

- Автоматическое создание новой версии при повторной загрузке файла с тем же логическим идентификатором.
- Просмотр истории версий: автор, время загрузки, комментарий.
- Сравнение метаданных версий (размер, количество строк, хэш содержимого).
- Кнопка «Восстановить» для переактивации предыдущей версии.

**UX/технические требования.**

- Таблица `file_versions` с полями `dataset_id`, `version`, `checksum`, `created_at`, `created_by`.
- Хранение бинарных данных в объектном сторидже с версионированием или отдельными префиксами.
- API для списка версий (`GET /api/v1/datasets/{id}/versions`) и отката (`POST /api/v1/datasets/{id}/versions/{version}/restore`).
- Лог аудита фиксирует действия восстановления.

**Зависимости.** Единый идентификатор датасета, права доступа на просмотр/откат, интеграция с существующим каталогом данных.

## Пре-просмотр популярных форматов — ★★, команда S/M

**Цель.** Пользователь проверяет корректность содержимого перед запуском тяжёлой обработки.

**Основные возможности.**

- Превью первых N строк для CSV/TSV и Excel (табличный вид, автоопределение типов).
- Отображение PDF прямо в браузере с возможностью пролистывания.
- Галерея миниатюр для изображений с возможностью увеличить до оригинального размера.
- Подсветка потенциальных проблем (битая кодировка, слишком длинные строки).

**UX/технические требования.**

- Лимиты по размеру превью (`PREVIEW_MAX_ROWS`, `PREVIEW_MAX_PAGES`).
- Для Excel — конвертация первого листа в HTML/JSON через `openpyxl`/`pyexcel`.
- Для PDF — генерация вьюеров через PDF.js, кеширование преобразованных страниц.
- Для изображений — создание миниатюр через Pillow с хранением в CDN/S3.

**Зависимости.** Инфраструктура для временных файлов превью, компонент фронтенда `DatasetPreview`, права на просмотр.

## Валидация данных на уровне схемы — ★★★, команда M

**Цель.** Предотвратить обработку некорректных данных благодаря автоматическим проверкам структуры и типов.

**Основные возможности.**

- Поддержка JSON Schema и pydantic-моделей для табличных датасетов.
- Конфигурируемые правила: обязательные колонки, типы, диапазоны значений.
- Отчёт о результатах валидации с категориями ошибок, предупреждений и предложениями исправлений.
- Интеграция с CI: блокировка публикации данных при критических нарушениях.

**UX/технические требования.**

- Хранение схем в таблице `dataset_schemas` с версиями и авторами.
- API `POST /api/v1/datasets/{id}/validate` и автоматический запуск после загрузки.
- Использование `pydantic`/`pandera` для табличных структур, `jsonschema` для JSON.
- Конфигурация порогов блокировки (`VALIDATION_BLOCKING_LEVEL`).

**Зависимости.** Каталог схем, UI для редактирования правил, уведомления об ошибках (email/Slack).

## Реестр задач — ★★, команда S/M

**Цель.** Предоставить прозрачность по всем обработкам: статусы, длительность, ошибки.

**Основные возможности.**

- Страница «Реестр задач» с фильтрами по датам, пользователю, типу задачи.
- Таймлайн выполнения с отображением этапов (загрузка → валидация → обработка → публикация).
- Детальная карточка задачи с логами и ссылкой на результат.
- Экспорт списка задач в CSV для отчётности.

**UX/технические требования.**

- API `GET /api/v1/tasks?status=&type=&user=` с пагинацией и сортировкой.
- Метрики длительности и ошибок сохраняются в `task_runs` (старт, окончание, статус, сообщение).
- Веб-сокеты или SSE для обновления карточек задач в реальном времени.
- Ролевые права: просмотр только своих задач или глобальный доступ для администраторов.

**Зависимости.** Централизованное логирование задач, доработка фронтенд-страницы мониторинга, интеграция с уведомлениями.
