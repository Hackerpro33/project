# Инкрементальные вычисления и материализованные представления

## Зачем нужны

Инкрементальные вычисления позволяют пересчитывать результат обработки данных
только для изменившегося подмножества исходных записей, снижая затраты на
процессинг и задержки ответа. Материализованные представления фиксируют
предварительно вычислённые результаты запросов и позволяют мгновенно
возвращать агрегированные данные без повторного чтения исходных таблиц.
Комбинация двух подходов уменьшает нагрузку на основную СУБД и сокращает время
ожидания аналитиков при работе с крупными датасетами.

## Когда применять

- **Регулярные пересчёты метрик.** Например, при поступлении новых загрузок в
  Insight Sphere можно пересчитывать только «грязные» сегменты, а агрегаты
  хранить в материализованных представлениях для дешёвого чтения. Это
  снижает время обновления дашбордов и отчётов.
- **Ресурсно ёмкие запросы.** Если аналитики часто выполняют сложные JOIN +
  GROUP BY запросы, материализация готовых агрегатов позволяет разгрузить
  production-базу и улучшить p95 задержки API. При этом инкрементальное
  обновление гарантирует, что данные в представлении остаются свежими без
  полного пересчёта.
- **Интеграции и обмен данными.** Сторонние сервисы могут потреблять
  материализованные снапшоты вместо непосредственного доступа к рабочим
  таблицам, что улучшает изоляцию и упрощает контроль версий.

## Архитектурные паттерны

1. **Ленивое обновление (on-demand refresh).** Представление помечается как
   устаревшее при изменении источников. Первый запрос после изменения
   инициирует фоновую инкрементальную пересборку. Подходит, если задержка в
   несколько секунд приемлема.
2. **Периодический refresh по расписанию.** Задания RQ или Airflow
   обновляют представление каждые N минут/часов. Используется, когда
   нагрузка на запись высокая, но SLA чтения допускает небольшую
   задержку. Можно комбинировать с отслеживанием «грязных» партиций.
3. **Триггеры/лог изменений.** Postgres Logical Decoding или Debezium
   отправляют события об изменениях, а воркеры пересчитывают только
   затронутые агрегаты. Самый свежий подход, но требует дополнительной
   инфраструктуры.

## Практические рекомендации

- Храните метаданные об успешных refresh-операциях (время, инициатор,
  продолжительность) в таблице мониторинга задач, чтобы быстро реагировать на
  деградации и SLA нарушения. Insight Sphere уже содержит требования к подобной
  таблице `task_runs`, их можно расширить полями о материализации (см.
  [спецификацию](./data_ingestion_feature_specs.md#реестр-задач----команда-sm)).
- Выбирайте стратегию refresh с учётом приоритетов SLA: для витрин, критичных к
  свежести, используйте события CDC; для аналитических отчётов — периодический
  график.
- Комбинируйте материализованные представления с кешированием на стороне API,
  чтобы минимизировать чтение из базы данных в пиковые часы.
- Планируйте окно обслуживания для полного пересчёта, чтобы гарантировать
  согласованность в случае накопления ошибок или изменения схемы.

## Связанные инициативы

- Реестр фоновых задач и расширенная телеметрия помогут контролировать
  длительность обновлений представлений и сигнализировать о сбоях (см. раздел
  «Реестр задач» в [спецификации загрузок](./data_ingestion_feature_specs.md#реестр-задач----команда-sm)).
- Версионирование файлов и схем облегчает повторную материализацию после
  отката данных: можно пересчитать только затронутые версии, а не весь
  исторический объём (см. раздел «Версионирование файлов» в той же
  [спецификации](./data_ingestion_feature_specs.md#версионирование-файлов----команда-m)).
- API `/api/dataset/{dataset_id}/materialized` предоставляет оперативные
  данные о состоянии материализованной витрины, включая исходный (baseline)
  снимок, дельту последнего обновления и накопленное отклонение от базовой
  версии. История refresh теперь хранит полный срез метрик для каждого
  события и соответствующую дельту относительно baseline, что позволяет
  быстро оценивать дрейф агрегатов во времени (реализовано в
  `backend/app/materialized_views_api.py`).
